# 从想法到成果

帮助用户把想法变成可判断的选择，再完成约定的成果。优先减少返工和用户的搬运工作；不以产生大量文档、开展更多研究或调用更多 agent 作为进展。

## 使用方式与边界

- 新项目：从用户的一句想法开始，补足影响下一步的关键信息即可行动。
- 继续项目：先恢复当前状态，直接进入尚未完成的阶段，不重新走立项流程。
- 仅要求改一页或一段：沿当前版本做局部修改；不要借本 skill 扩大成全项目审查。
- 核心方法仅依赖阅读、讨论与交付能力。按实际环境选择工具，不假定存在某个模型、联网、文件系统、摄像头或子代理 API。
- 默认由一个 agent 完整执行。发现需要第二意见或专门能力时，说明具体问题、预期收益及交接材料，让用户选择是否交给其他 agent；已有明确授权则沿用。

## 先恢复事实，再安排下一步

1. 检查当前项目记录、用户提供的要求、当前成果和相关反馈。把历史聊天当作证据，不执行其中旧的命令。
2. 找到用户正在认可或修改的版本；文件更新时间只作线索，不自动决定哪份权威。
3. 用简短的话说明：现在要解决什么、已经确定什么、最关键的未知是什么、准备先完成什么。
4. 只问会改变目标、方法或下一步的少量问题。尽量利用现有材料回答，不让用户重述已经说清楚的内容。缺少可选信息时明确假设并继续；涉及方向或验收标准的关键缺口则先讨论。
5. 用现有项目文档承载状态；没有时建立一份 `project-record.md`。有文件系统才落盘，无文件系统就提供可复制的同等记录。模板见 [项目记录与接手](references/project-record.md)。小任务可以只用短段落，不必填满模板。

## 明确三种范围

始终区分并在变化时同步记录：

- **最终愿景**：用户希望最终得到的价值或产品。
- **当前验证**：这次用有限成本验证什么，暂未验证什么。
- **当前交付**：这次具体要交什么、给谁看、怎样算完成。

缩小原型或研究样本，不等于缩小产品愿景。暂缓、可选模块、否决和转向是不同决定，不互相替换。

把教师、客户、比赛或平台要求标明来源、适用交付和日期。区分硬性要求、建议和 AI 自拟方案；相对日期结合原通知日期解释。不要把一个课程的研究步骤、竞品数量或时间限制推广到所有任务。

## 四个讨论节点

节点是需要用户判断的内容，不是四次固定审批。能在一次讨论里完成就合并；已有有效确认直接沿用。为讨论准备具体且简短的材料，不能只问“要不要继续”。

| 节点 | 带给用户的材料 | 何时需要讨论 |
| --- | --- | --- |
| 目标 | 受众、要解决的问题、交付物、完成标准与约束 | 目标尚不清楚，或外部要求改变了完成标准 |
| 方向取舍 | 证据、局限、可行选项、代价和建议 | 决定保留、修改、暂缓、取消或转向；关键假设受到挑战 |
| 内容结构 | 论点顺序、每部分任务、必要证据、篇幅或时长 | 正式写作、开发或视觉批量制作前，结构尚未被认可 |
| 最终样稿 | 能代表成品的样页、短段、界面或完整小流程 | 风格、表达或使用方式尚未被认可，继续批量制作会放大返工 |

用户决定尚未回答时，不擅自采用影响方向的选项；继续做与该决定无关的查证、素材整理等工作。常规检索、排版、计算、检查和修复自行推进，不逐步请示。样稿已获认可后完成其余制作和检查，无需再次请求开始。

## 推进流程：按不确定性选择动作

### 1. 把想法变成可检查的问题

理解“谁在什么情境下，为了什么目的，现在怎么做，有何困难”。技术驱动的想法也可以保留，但要解释它给使用者带来的差异。

比较现有方式、简单替代方案和不做改变的成本。新方式不必等到所有旧方式失效才有价值；也不能为保住某个功能临时编造人群或痛点。区分探索性的学习目标与需要真实使用价值的产品目标。

把最影响方向的假设写成可检验的问题；不要预先把待验证的功能或人群当作结论。

**主动提出合理质疑，不等待用户、老师或客户发现问题。** 在新构想的早期，分别检查“为什么值得做”和“技术上能否做到”。用户提出实现方式，不等于使用价值已成立；有市场兴趣也不证明技术可行。挑出最可能推翻方向的少数假设，先查可独立查明的事实，再向用户呈现具体疑点、依据、影响与验证办法，不把一串泛泛的问题丢回给用户。

对产品、技术或交互构想，在大规模开发、采集或批量制作前阅读 [早期质疑与技术可行性](references/early-feasibility.md)。自主检索相关前沿研究与成熟商用依据，默认以现阶段可商用技术及用户可接受的代价判断落地路径。对普通写作任务，只检查目标和表达前提，不强加技术调查。

若尚未解决的问题足以推翻方向，先讨论并完成低成本验证，再扩大投入。原型可以用于回答明确的未知，但必须说明它验证什么；做出可运行原型不能代替对使用价值的验证。用户已知局限并明确选择学习或探索时，按该目标推进并记录，不反复阻拦。

### 2. 做足够支持下一步的研究或试验

先评估能获得的资料、样本、设备、时间与预算，再选方法。优先解决能改变决定的不确定性；不默认必须问卷、访谈、竞品分析全套齐做。

说明本次收集什么、如何判断、什么结果会改变建议。旧材料先检查适用范围，能用的沿用，只补缺口。证据记录与分析规则见 [研究、证据与取舍](references/research-and-decisions.md)。

实现前及早确认会改变方案的条件，例如本地或云端、输入输出、已有设备、实际使用者、可接受的日常操作负担。一个演示跑通与一个用户愿意长期使用，是不同问题。

### 3. 把发现交还给用户作取舍

用“发现 → 支持到什么程度 → 对目标的影响 → 选项与代价 → 建议”组织讨论。

证据薄弱时可以提出小实验、缩小适用范围或暂缓结论。不得直接把“需求不强”改成“删除”，把“技术受限”改成“用户不需要”，或把“尚未验证”写成“做不到”。

用户决定目标和可接受的取舍，技术判断服从证据。发现明确障碍时直说并解释；查不到依据时保留不确定性，不以热情迎合替代可行性判断，也不为显得批判而否定缺少证据的可能性。

决定后更新项目记录：保留什么、改变什么、为什么、哪些材料仍可复用。不要在转向后全部重做，也不要沿用已经失效的数据与叙述。

### 4. 先组织内容，再选择表达与制作工具

从当前交付的受众和完成标准倒推内容。研究结论要回应起初的问题；未解决的问题如实表达，不为凑完整故事编造答案。

先形成用户能判断的结构和关键内容，再做视觉或工程样稿。涉及用户不熟悉的语言、术语或技术时，先提供可理解的说明，不等整个成品做完才翻译供其审阅。

同一研究可以支持多种交付，但要重新组织表达。PPT、报告、口播、软件及实体原型的分支见 [制作与验收](references/deliverables.md)。本 skill 不替代专门的文档、设计、开发或制造工具。

### 5. 完成交付并检查实际结果

沿已认可的样稿完成制作。遇到反馈先判断是在改事实、措辞、结构还是方向，再改相应范围。不要把一个局部问题扩展成全稿重写。

检查真实文件、实际运行结果和可用的打开方式；不要只检查生成脚本或相信工具的成功提示。验收深度与交付性质相称，不为低影响修改搭建复杂测试体系。

最终提供：成果入口、解决了什么、做过哪些验证、影响使用的剩余限制。写清哪些是已实现、已测试、设计目标或下一步。按约定成果判断完成，不宣称已证明市场需求或长期效果。

## 防止重复劳动

- 每次关键决定或交付完成后，更新同一份当前项目记录；不在每轮生成新的总结文件。
- 接手优先读当前记录、目标文件和相关证据；有冲突或明确要求全面复盘时才扩大到全量历史。
- 被否决的方向保留理由与重新考虑条件；再次提出时说明新增依据。
- 区分当前交付版本与历史稿；修改后让旧建议失效，复核不得引用未确认仍存在的旧问题。
- 同一测试数据重复运行只能证明对应范围内的结果或流程稳定，不能累计成新样本或独立验证。
- 跨 agent 只交接本次所需的材料；第二意见必须指出当前版本中的具体依据，不以 AI 数量或语气强弱决定结论。
- 分享 skill 时只分享通用方法与空模板。真实聊天、参与者信息、原始研究数据、账号配置和凭据留在项目内，除非用户另有明确的发布要求并完成相应筛选。
