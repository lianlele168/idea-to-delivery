# 早期质疑与技术可行性

仅适用于涉及实际技术或工程实现的任务，包括软件、技术产品及功能性交互的立项、重大功能增加和方向调整。纯内容或表达任务使用 [研究、证据与取舍](research-and-decisions.md) 与 [制作与验收](deliverables.md) 的对应分支；技术题材本身不触发工程可研。混合项目只对需要实现的部分应用本文件。

目标是在低成本阶段暴露会导致大返工的问题。按项目约定区分现实部署、商用交付与科研、学习或概念探索，不默认所有技术任务都要达到商用成熟度。

## 同时检查价值与实现

| 判断 | 要弄清什么 | 不足以替代判断的材料 |
| --- | --- | --- |
| 值得做吗 | 具体谁在什么情境下完成什么任务；相对现有方式的净收益 | 用户喜欢概念、市场规模大、演示看起来新颖 |
| 能做到吗 | 科学依据、可用技术、组合后的工程约束及代价 | 需求强烈、单项论文结果、未经验证的架构图 |

两项可以并行。任一项存在可能推翻方向的缺口，就先针对该缺口做小调查或试验，避免先做完整产品再寻找理由。已知答案的部分不反复证明。

## 合理质疑的做法

1. 复述用户真正要达到的效果，分开目标与实现方式。用户提出一种具体方式时，检查它服务的目标是什么，以及是否存在其他可比较的路径。
2. 把现有方式与新方式放到同一个具体任务中比较。检查操作次数、速度、出错代价、环境限制、学习与维护负担等真正相关的维度。
3. 提出最有可能改变选择的反例：在哪种常见条件下，新方式收益消失或代价超过收益？这个条件在目标场景中是否常见？
4. 检索能独立查明的事实。涉及个人意图、真实使用经历或价值偏好时再向用户追问，不让用户代替 AI 做资料调查。
5. 给出下一步：继续的理由、需要修改的部分、最小验证动作，或暂缓投入的具体原因。质疑应帮助用户决策，不能停在“这个想法不行”。

不要机械反对，也不要临时发明特殊人群来维护原设想。现有方式尚能工作，不代表新方式没有价值；新方式需要能说清在某些条件下的收益，而非必须证明所有替代方式都失效。

若项目目的明确是学习技术、艺术表达或探索交互，可按该目的验收；不能擅自要求它证明商业购买意愿。把探索原型与产品价值验证分别标明。

## 自主技术调查

先把设想拆成关键能力及它们的相互约束，再检索。优先调查可能导致路线更换、成本陡增或无法交付的部分，避免无目的地汇编前沿新闻。

- **科学与前沿依据**：关键能力存在研究层面未知时，查相关原始论文、实验条件、研究限制；必要时查可靠的基础原理资料。已有成熟实现且没有相关未知时，不为凑报告强行追前沿。
- **商用与工程依据**：厂商技术文档、数据表、官方接口及限制、可采购组件和已有系统；相关标准使用官方或可核验来源。
- **系统组合**：各部分分别能工作后，整体是否仍满足目标。软件关注接口能力、数据条件、权限、性能或运维等相关限制；实体系统按需关注尺寸、功耗、发热及结构等限制。只查与具体方案相关的约束。
- **落地代价**：区分一次性开发/验证费用与单件或持续使用成本；注明数量、条件和估算依据。没有可靠报价时给成本驱动因素，不编造精确金额。

凡涉及当前成熟度、供应情况、接口能力或成本的关键结论，使用可访问的最新相关资料查证。保留来源链接、日期、实际支持的判断和条件。优先一手资料，不将营销描述、专利存在或 AI 总结直接当作系统可实现的证明。

需要核查时先使用当前可用的检索和读取工具；不能因本 skill 跨平台而假定无法联网。只有确认工具缺失或实际访问受限，且合适的替代途径仍不能取得必要依据时，才给出受限条件下的初判，并记录已尝试的动作与未核查项。不得声称已查阅前沿资料，也不能把“没搜到”写成“科学上不可能”。

## 结论要分层并带条件

| 层次 | 合理的结论形式 |
| --- | --- |
| 科学依据 | 与已知原理明确冲突 / 尚缺支持 / 在说明的条件下有依据；强否定需足够依据 |
| 技术成熟度 | 理论设想、论文实验、研究样机、商用组件、已有完整系统；不跨级推断 |
| 本项目落地 | 可采用成熟路径 / 需要组合开发和验证 / 代价超过现有约束 / 关键条件尚不明确 |

区分“小样可行”“完整系统可行”和“用户预算与能力范围内可行”。以现实部署或商用交付为目标时，优先从现阶段可用的成熟技术寻找路径。若用户明确选择科研、学习或概念探索，则按研究问题、实验结果或概念边界验收；可以采用未商用技术，但须说明假设与局限，不能将探索成果包装成已具备商用能力。

每个会影响决定的结论同时说明证据强弱、适用条件和未知。不要只说“可以实现但有挑战”。

## 给用户看的最小结果

材料较少时用几段话，复杂时用表格；无需固定报告篇幅。

```text
要实现的效果及候选方式：
最关键的价值疑点：现有替代方案是什么，新方案收益在哪里？
关键技术能力：证据来源、成熟度、系统约束及尚未确认的部分。
可选路径与代价：能保留什么，必须妥协什么，成本依据是什么？
建议：继续 / 修改 / 小实验 / 暂缓，以及理由。
下一步验证：回答哪个问题，用什么最小动作，什么结果会改变建议？
需要用户判断：真正涉及目标或取舍的选择；已有答案直接沿用。
```

如果疑点足以使后续工作失去意义，先回到方向取舍节点；与疑点无关的工作可继续。不要把暂停扩大投入误变成禁止所有探索，也不要以用户说过“做出来”为由跳过刚发现的重大障碍。

## 验证动作要对应未知

若主要未知是新方案相对现有方式的价值，先做场景比较或低成本体验验证；若主要未知是关键能力能否实现，优先做技术试验。根据本项目证据选择动作，不能把技术演示成功当作使用价值成立，也不能因单项能力可用就断言整个系统成熟。
